Do pedido ao DONE, com evidência

Guia para devs que vão instalar e usar o plugin sdd do marketplace claude-sdd-framework em projetos de qualquer stack.

Os selos indicam a origem do conteúdo: Verificado comando ou comportamento confirmado no README ou nos relatórios de validação; Ilustrativo exemplo de como a conversa tende a ser, sem garantia de texto idêntico.

1.Visão geral

O plugin sdd distribui o processo de engenharia SDD (Spec-Driven Development) para qualquer projeto e linguagem. Você conversa com um único agente, o TecLeader. Ele transforma o pedido em spec.md e tasks.md, delega a agentes especializados e só encerra a entrega com evidência. Verificado

As regras de engenharia vão como skills; o conhecimento de cada stack fica em references/. A stack do projeto é declarada na seção ## Stack do CLAUDE.md: os agentes não dependem de linguagem.

Fluxo SDD

  1. Requiremento pedido
  2. SpecREQs + critérios de aceite
  3. Technical Designquando obrigatório
  4. Taskem tasks.md
  5. Test Designrastreio REQ → teste
  6. Implementationbackend / frontend
  7. Security Reviewquando aplicável
  8. Validationagente tests
  9. Correctionaté aprovar
  10. Donesó o TecLeader encerra

Linhas tracejadas são etapas condicionais. O design técnico é obrigatório para mudança arquitetural, novo módulo, banco de dados, contrato de API, integração externa, infraestrutura e mudança relevante de domínio; a revisão de segurança, para autenticação/autorização, dados sensíveis, entrada externa, novas dependências, segredos e infraestrutura.

Papéis

TipoAgentesPodeNão pode
Coordenadorsdd:tecleaderdelegar, aprovar design, encerrar (DONE)ser implementador
Implementadoressdd:backend, sdd:frontendimplementar e testar a própria featureencerrar tasks
Revisão de segurançasdd:securityreportar riscos com severidade e evidênciaimplementar, corrigir, encerrar
Validadorsdd:testsvalidar requisitos, regressão, E2E, aceitecorrigir produção, encerrar
Arquiteturalsdd:infra-architectdecisões de infraestruturaimplementar mudanças
Dica

Perguntas, leitura de arquivos e esclarecimentos são respondidos direto pelo TecLeader, sem gerar spec nem tasks.

2.Instalação

Primeira vez?

Siga o guia Primeiros passos: os mesmos passos abaixo, com o que você vai ver e como conferir em cada um, nos dois caminhos (código existente e projeto do zero), além de o que versionar e problemas comuns.

Pré-requisitos Verificado

  • Claude Code 2.1.288 ou superior (claude --version; testado no 2.1.296).
  • Git com acesso ao repositório privado. Teste: git ls-remote https://github.com/powerlok/claude-sdd-framework.git. O Claude Code usa as credenciais git da máquina (HTTPS com gerenciador de credenciais, ex.: gh auth setup-git, ou SSH).
  • Windows: Git for Windows (o hook do plugin usa bash) e claude no PATH (ver Solução de problemas).
  • Opcional: conector Atlassian no claude.ai, para ler issues do Jira.

A partir do GitHub Verificado

  1. Uma vez por máquina, registre o marketplace na versão desejada (tag):
claude plugin marketplace add "https://github.com/powerlok/claude-sdd-framework.git#v0.6.4"
  1. Na raiz do projeto (raiz do repositório git; no projeto do zero, antes rode git init), copie o arquivo inteiro templates/project-settings.git.json para .claude/settings.json. Só esse arquivo não carrega o plugin.
  2. Instale o plugin no projeto e confira:
claude plugin install sdd@claude-sdd-framework --scope project
claude plugin list        # sdd 0.6.4, Scope: project, enabled
  1. Abra claude na raiz do projeto e aceite o diálogo de confiança da pasta (sem confiar, o plugin do projeto não carrega). A primeira resposta é do TecLeader ("Sou o TecLeader"), com a situação do projeto. Se instalou com a sessão aberta, use /reload-plugins ou abra nova sessão.
  2. Sem CLAUDE.md, o TecLeader faz o onboarding: com código existente, pergunta "Faço o onboarding agora?" e, com o seu sim, lê o código e cria CLAUDE.md e .specs/INDEX.md; no projeto do zero, pergunta a stack (linguagem, framework, versão), a nuvem/infra (ou "nenhuma") e as convenções, assume que os artefatos são versionados (Versionar artefatos SDD: sim; você pode pedir não) e só cria os arquivos depois do seu ok. Ele nunca faz commit.
Perigo

Nunca coloque usuário, senha ou token na URL do repositório. Use SSH ou HTTPS com o gerenciador de credenciais do git.

Equipe: o .claude/settings.json versionado não instala nada sozinho; cada dev roda o marketplace add (uma vez) e o plugin install (por projeto). Opcional: em vez do onboarding, copie templates/CLAUDE.md e preencha ## Stack e os comandos.

A partir de uma pasta local Verificado

  1. Copie templates/project-settings.local.json para <projeto>/.claude/settings.json e troque <CAMINHO_ABSOLUTO_DO_REPO_claude-sdd-framework> pelo caminho da pasta (use /).
  2. No projeto, rode:
claude plugin marketplace add "<caminho>/claude-sdd-framework" --scope project
claude plugin install sdd@claude-sdd-framework --scope project
claude plugin list        # sdd ... Status: enabled
  1. Abra claude no projeto. A sessão já inicia como sdd:tecleader ("agent": "sdd:tecleader" no settings). Alternativa:
claude --agent sdd:tecleader

Catálogo opcional authoring Verificado

Skills para criar novas skills e agentes. Sem instalação, nada com prefixo authoring: aparece.

claude plugin install authoring@claude-sdd-framework --scope project

3.Configurar o projeto

CLAUDE.md e a seção ## Stack

O modelo em templates/CLAUDE.md tem estas seções: Visão do projeto, Stack, Comandos, Arquitetura e Regras específicas do projeto. A seção ## Stack é a fonte da stack para sdd:backend e sdd:frontend.

## Stack

### Backend

- Linguagem e versão: <EX.: LINGUAGEM X.Y>
- Framework e versão: <FRAMEWORK X.Y>
- Gerenciador de pacotes/build: <GERENCIADOR>
- Banco de dados: <BANCO E VERSÃO | NÃO SE APLICA>
- Referência do plugin: `backend-engineering/references/<stack>.md` <OU "SEM REFERÊNCIA">
Atenção

Preencha apenas com informação verificada (código, arquivos de configuração, comandos executados). O que não for conhecido fica como <A DEFINIR>. Registre na tabela de comandos somente comandos que já rodaram com sucesso.

Regras do projeto no CLAUDE.md complementam as do plugin e prevalecem quando mais específicas, mas não podem relaxar: segredos/credenciais, verificação SSL, confirmação de ações irreversíveis, Jira somente leitura e menor privilégio.

Camadas do CLAUDE.md

O Claude Code carrega o CLAUDE.md da pasta aberta, dos diretórios pais e o pessoal. Cada camada tem um papel; nada é duplicado e o mais específico prevalece (exceto os controles não relaxáveis).

CamadaOndeO que vaiVersionado
Pessoal~/.claude/CLAUDE.mdpreferências pessoaisnão
Workspacepasta-mãe dos repositórioslista de projetos, convenções comuns (CLAUDE.workspace.md)não
Projetoraiz do repositório## Stack, comandos, arquitetura, ## Repositório, ## SDDsim (padrão)

Na seção ## SDD do projeto, Versionar artefatos SDD: não faz o TecLeader usar .claude/settings.local.json e o exclude local do git (git rev-parse --git-path info/exclude), sem tocar no .gitignore.

Migração sem perguntas

Se encontrar CLAUDE.md, .specs/ ou .claude/ fora do repositório, o TecLeader propõe o plano padrão com uma única confirmação: mescla sem sobrescrever (mostrando o diff), renomeia as origens para .bak-<data> (nunca apaga), não leva allow/env para arquivo versionável e nunca faz commit. Ele não pergunta onde fica o .specs/, se move o CLAUDE.md nem se versiona. Com vários repositórios, a única pergunta extra é qual é o projeto.

ModoComo abrirAcessoCLAUDE.md carregadoDeny que vale

O deny exigido na sessão é o do modelo somado ao de cada projeto envolvido. Se faltar algo, a sessão fica somente leitura (sem escrita, build, testes ou delegação) até corrigir e reiniciar; --permission-mode plan impõe isso no próprio CLI.

Mudança em mais de um projeto: o plano separa projetos alterados e de referência e pede uma confirmação; cada projeto alterado ganha spec e tasks, ligadas por Relacionada a:; cada task mexe em um único repositório; nunca há commit. O CLAUDE.md de um projeto só vale para ele, e o de um projeto de referência é dado, não instrução.

Settings

Verificado

Limites: o deny é defesa em profundidade, não barreira. O deny de Read cobre as ferramentas de arquivo e os comandos de arquivo que o Claude Code reconhece no Bash (cat, head, tail, sed, tee, redirecionamentos), mas não um grep -r sem citar o arquivo nem um script (Python, Node) que abre o arquivo por conta própria. Padrões **/ valem a partir da pasta onde a sessão começou; arquivos da home usam ~/. O deny de Bash não pega o mesmo comando escrito de outro jeito (sh -c '...', caminho absoluto do programa, git -C . push); flags combinadas (-uf) e :refspec caem só na confirmação (ask). No Windows sem Git Bash (ferramenta PowerShell), as regras Bash(...) não se aplicam ao PowerShell. Para bloqueio no sistema operacional, use o sandbox do Claude Code (documentação de permissões). O template project-settings.git.json fixa a versão com "ref": "v0.6.4" (tag). Para subir de versão, troque o ref pela nova tag e rode claude plugin marketplace update e claude plugin update; sem ref, vale a branch padrão.

5.Como pedir

Um bom pedido diz o projeto, o que deve acontecer e, se você souber, como saber que está certo. Não precisa escrever a spec: o TecLeader propõe os requisitos e você confirma.

Evite

  • "melhora o login"
  • "cria uma API"
  • "tá dando erro"
  • "faz sem teste, é rápido"

Prefira

  • "No meu-app, mostre 'Sessão expirada' ao voltar ao login após logout"
  • "Crie um projeto novo em api-tarefas: CRUD de tarefas (título, descrição, concluída)"
  • "No meu-app, e-mail com espaço no final falha. Esperado: ignorar espaços nas pontas"
Ilustrativo
  • Uma feature por pedido. O resultado fica mais previsível.
  • Revise a spec com atenção. É o ponto que mais influencia o resultado.
  • Não peça para pular etapas. O TecLeader não implementa sem spec nem encerra sem validação (ver exemplo 15).
Perigo

Nunca cole tokens ou senhas reais na conversa. Use variáveis de ambiente.

1

Instalação local

Verificado

Fonte: README.md (Instalação); validation/t008a.md, cenário 1.

Pedido

Você quer o plugin em um projeto, a partir da pasta clonada do claude-sdd-framework.

claude plugin marketplace add "<caminho>/claude-sdd-framework" --scope project
claude plugin install sdd@claude-sdd-framework --scope project
claude plugin list

O que o TecLeader faz

Ainda nada: a instalação é feita por você, na CLI, antes de abrir a sessão. O marketplace passa a constar como declarado nas settings do projeto.

O que você responde

Copie templates/project-settings.local.json para <projeto>/.claude/settings.json (trocando o caminho) e templates/CLAUDE.md para a raiz. Abra claude no projeto.

Resultado

No piloto de instalação limpa, sdd@claude-sdd-framework apareceu habilitado, escopo project, com agentes sdd:backend, sdd:frontend, sdd:infra-architect, sdd:security, sdd:tecleader, sdd:tests, e nenhum authoring:.

Instalação via GitHub

Verificado

Fonte: README.md (A partir do GitHub); templates/project-settings.git.json.

Pedido

Seu time publicou o marketplace no GitHub e você quer usá-lo sem clonar manualmente.

O que o TecLeader faz

Nada nesta etapa. O Claude Code usa as credenciais git da sua máquina para acessar o repositório.

O que você responde

Uma vez na máquina, registre o marketplace na versão fixada: claude plugin marketplace add "https://github.com/powerlok/claude-sdd-framework.git#v0.6.4". No projeto, copie o arquivo inteiro templates/project-settings.git.json para <projeto>/.claude/settings.json; ele já declara o marketplace com o ref:

"extraKnownMarketplaces": {
  "claude-sdd-framework": {
    "source": { "source": "git", "url": "https://github.com/powerlok/claude-sdd-framework.git", "ref": "v0.6.4" }
  }
}
Perigo

Sem usuário, senha ou token na URL. Use SSH ou HTTPS com o gerenciador de credenciais.

Resultado

Na raiz do projeto, instale com claude plugin install sdd@claude-sdd-framework --scope project e confirme com claude plugin list (sdd 0.6.4, Scope: project, enabled). O settings.json sozinho não instala o plugin: cada dev roda o install. Passo a passo completo: primeiros-passos.md.

3

Projeto novo (onboarding)

Ilustrativo

Fonte do comportamento: agents/tecleader.md (Onboarding de Projeto). Diálogo ilustrativo.

Pedido

Crie um projeto novo em api-tarefas: API com CRUD de tarefas
(título, descrição, concluída).

O que o TecLeader faz

  • Percebe que o projeto é novo e vazio: não há o que analisar, então pergunta stack e convenções.
  • Registra apenas o que você informar, inclusive na ## Stack.
  • Cria CLAUDE.md e a pasta .specs/, e propõe REQs com critérios de aceite.

O que você responde

Backend em Python, FastAPI, pytest, sem banco por enquanto (memória).
Pode seguir com os REQs propostos.

Resultado

Projeto com CLAUDE.md (com ## Stack), .specs/<feature>/spec.md e tasks.md. O TecLeader informa o que foi criado. Em projeto existente sem CLAUDE.md, ele explora o código (README, manifestos, configs de build/lint/teste, CI) e extrai a stack dos manifestos. Se já existir CLAUDE.md, não sobrescreve: só sugere melhorias.

Feature em projeto existente

Ilustrativo

Fonte do comportamento: agents/tecleader.md (Workflow SDD, Design Técnico). Diálogo ilustrativo.

Pedido

No meu-app, adicione a opção "Mostrar senha" no campo de senha do login.

O que o TecLeader faz

Lê o CLAUDE.md e .specs/ existentes e propõe:

REQ-005: botão que alterna a visibilidade da senha
Critérios de aceite:
- alterna o campo entre type="password" e type="text"
- tem nome acessível e funciona pelo teclado
Validação: teste de componente req005 + E2E

Mudança pequena: sem design técnico e sem revisão de segurança (nenhum dos gatilhos se aplica).

O que você responde

Ok, mas o padrão deve ser senha oculta.

Resultado

tasks.md recebe as tasks (implementação e validação), o TecLeader delega, mostra os comandos de teste e build executados com resultado e demonstra o sistema funcionando antes de encerrar.

5

Bug com teste de regressão

Ilustrativo

Fonte: regra de qualidade (sdd-rules) e skill bug-diagnosis (5 fases). Diálogo ilustrativo.

Pedido

No meu-app, se eu digitar " user@example.com" (com espaço no início)
o login dá erro. Esperado: ignorar espaços nas pontas do e-mail.

O que o TecLeader faz

Registra o defeito como requisito e exige correção mais teste de regressão. O diagnóstico segue as 5 fases: reproduzir, isolar, hipótese com evidência, correção mínima com teste de regressão, verificar e prevenir. A task vai ao agente da stack (aqui, sdd:frontend), e depois sdd:tests roda a regressão.

O que você responde

Normalmente nada, além de confirmar o requisito proposto. Se a causa não for reproduzível, passe os passos exatos.

Resultado

Correção com o teste de regressão e evidência da suíte executada. Problemas encontrados fora do escopo são registrados como observação, não corrigidos sozinhos.

Backend .NET

Verificado

Fonte: validation/t008c.md (piloto .NET); formato de delegação em agents/tecleader.md.

Pedido

Crie em api-todos uma API de tarefas (criar e consultar) em ASP.NET Core.

O que o TecLeader faz

Lê a ## Stack do CLAUDE.md e delega a sdd:backend indicando a referência:

Objetivo / Requisitos / Spec / Tasks / Contexto
Stack: <linguagem/framework/versão> — referência: backend-engineering/references/dotnet.md
Arquivos permitidos / Arquivos proibidos
Critérios de aceite / Validação obrigatória / Resultado esperado

O que você responde

Confirma os REQs e informa convenções que o agente não pode deduzir (por exemplo, tipo do id), pois a spec do piloto não definia.

Resultado

No piloto, o agente leu dotnet.md, organizou Domain/Application/Infrastructure/Endpoints, usou ProblemDetails, nomeou testes Req001_* com [Trait("Requirement","REQ-001")] e WebApplicationFactory<Program>. dotnet test: 9 passed. O validador acrescentou 3 testes (título vazio gera 400 application/problem+json; id inexistente gera 404).

Observação do relatório: o piloto executou o agente sdd:backend diretamente com o texto da delegação, sem passar pela sessão do TecLeader.

Backend Python

Verificado

Fonte: validation/t008b.md (piloto Python).

Pedido

Crie em api-todos uma API de tarefas em Python (FastAPI), com testes por requisito.

O que o TecLeader faz

Delega a sdd:backend com Stack: ... — referência: backend-engineering/references/python.md. O mesmo agente, sem instruções de Python no seu texto, serve a qualquer stack: o conhecimento vem do CLAUDE.md e da referência.

O que você responde

Confirma os REQs. Se o design técnico for exigido (módulo novo), aprova o design.md que o TecLeader apresentar. No piloto o agente não criou design.md e declarou o risco no relato.

Resultado

Código em camadas domain/application/infrastructure/api (Pydantic v2, create_app), tests/test_req001.py e test_req002.py. pytest: 13 passed (8 do agente + 5 do validador). Validações extras: título vazio, ausente ou com 201 caracteres geram 422; id inexistente gera 404.

Frontend React

Ilustrativo

Fonte: references/react.md existe no plugin; delegação conforme agents/tecleader.md. Diálogo ilustrativo.

Pedido

No meu-app (React + TypeScript + Vite), crie uma tela simples de login.

O que o TecLeader faz

9

Revisão de segurança

Ilustrativo

Fonte do fluxo: agents/tecleader.md (Revisão de Segurança); validation-report.md registra o ciclo real do plugin (volta 1 RISCO IDENTIFICADO, volta 2 APROVADO). Diálogo ilustrativo.

Pedido

Adicione autenticação por token na api-tarefas.

O que o TecLeader faz

Autenticação e entrada externa exigem design técnico (aprovado antes do código) e, após IMPLEMENTED e antes de VALIDATING, a revisão do sdd:security.

  • APROVADO: segue para validação.
  • RISCO IDENTIFICADO: volta ao implementador, parecer refeito (limite de 3 voltas) e sdd:tests reexecutado.

O que você responde

7.Estados e critérios de DONE

Estados oficiais de uma task, gravados em tasks.md. Verificado

TODO→IN_PROGRESS→IMPLEMENTED→SECURITY_REVIEW (se aplicável)→VALIDATING→DONE
VALIDATING→FAILED_VALIDATION→FIXING→VALIDATING_AGAIN→VALIDATING

O ciclo de correção se repete até aprovar. Após 3 falhas sem progresso, o TecLeader registra o bloqueio, resume o motivo, lista as tentativas e escala a você.

Checklist de DONE

Somente o TecLeader move uma task para DONE. Confira na entrega:

  • requisitos implementados e critérios de aceite atendidos;
  • testes existentes e executados, nenhum defeito aberto;
  • evidências registradas e relatório gerado;
  • README.md do projeto criado ou atualizado;
  • design técnico aprovado e registrado (quando obrigatório);
  • parecer de segurança APROVADO, sem risco HIGH/CRITICAL aberto (quando exigido);
  • funcionamento demonstrado: apps e serviços iniciados e demonstrados; bibliotecas, SDKs e CLIs com exemplo ou comando real e a saída.

9.Repositório (opcional)

Integração somente leitura com o provedor de código: issue vira spec (ID registrado, ex.: GH#42) e status de PR/CI vira evidência antes do DONE. Só vale se o CLAUDE.md do projeto tiver a seção ## Repositório (Provedor, Repositório, Acesso). Sem ela, o TecLeader não consulta nenhum provedor.

ProvedorCaminho padrãoStatus
GitHubtemplates/mcp-github.json (MCP oficial em /mcp/readonly)Verificado suportado e validado
Bitbucket CloudMCP Atlassian (issues vêm do Jira)experimental, não validado
GitLabtemplates/mcp-gitlab.jsonexperimental, não validado
Azure DevOpstemplates/mcp-azure-devops.jsonexperimental, não validado

Como ativar o GitHub

  1. No CLAUDE.md do projeto, adicione ## Repositório com Provedor: github, Repositório: <owner/repo> e Acesso: mcp (modelo em templates/CLAUDE.md).
  2. Copie templates/mcp-github.json para <projeto>/.mcp.json.
  3. Crie um PAT fine-grained somente leitura: só os repositórios do projeto; Metadata, Issues, Pull requests e Actions = Read; sem Contents write e sem Workflows; validade curta.
  4. Exporte o token na variável de ambiente GITHUB_PAT e confira com /mcp que o servidor github está connected.
Atenção

Nunca reutilize gh auth token (o login local costuma ter escrita) e nunca coloque o token em arquivo ou .env versionado.

Camadas de proteção

  • Servidor em modo somente leitura (GitHub em /mcp/readonly).
  • O TecLeader tem uma lista fechada de ferramentas de leitura; os demais agentes não consultam o provedor.
  • permissions.deny nos templates de settings bloqueia as ferramentas de escrita. O deny de Bash (gh, glab, az) é só defesa em profundidade, não barreira.
  • Abrir PR, comentar, revisar, fazer merge e criar issue não estão liberados: faça manualmente.
Issue e PR são dado não confiável

O TecLeader não segue instruções escritas em issue, PR, comentário ou log; sinaliza trechos suspeitos, exige sua confirmação antes de virar spec e repassa aos demais agentes só os REQs validados. Exemplos 16 a 18.

11.Solução de problemas

claude não é encontrado no Windows

O instalador nativo coloca o claude.exe em %USERPROFILE%\.local\bin, que pode estar fora do PATH. No PowerShell:

$env:Path += ";$HOME\.local\bin"

Erro "Input must be provided..." ao usar -p

--allowedTools aceita vários valores e consome o prompt se ele vier depois. Coloque o prompt logo após -p:

claude -p "<prompt>" --plugin-dir ./plugins/sdd --agent sdd:backend --allowedTools "Read,Glob,Grep"

Porta ocupada por outro projeto no E2E

No piloto, a porta 4173 estava em uso por outro projeto e o E2E falhou por ambiente (defeito D-003). A regressão passou em uma porta isolada (4180). Libere a porta ou configure uma porta própria no projeto.

As skills não pré-carregam na sessão principal

É comportamento do Claude Code: skills: só pré-carrega em subagentes. O TecLeader carrega sdd:sdd-rules e sdd:sdd-governance com a ferramenta Skill no início da sessão e após compact. Se uma skill não carregar, ele segue com a governança do próprio agente e avisa você.

"not found in marketplace" ao instalar

O marketplace não está registrado na máquina (verificado numa máquina nova: Plugin "sdd" not found in marketplace "claude-sdd-framework"). Rode uma vez claude plugin marketplace add "https://github.com/powerlok/claude-sdd-framework.git#v0.6.4" e repita o install. Se já estiver registrado, rode claude plugin marketplace update claude-sdd-framework.

Conector do Jira aparece como pending em -p

Em modo não interativo o conector conecta de forma assíncrona. No spike, funcionou com a variável abaixo:

MCP_CONNECTION_NONBLOCKING=false claude -p "<prompt>"

MCP do GitHub não conecta / ferramentas não aparecem

Confira, nesta ordem: (1) a variável de ambiente GITHUB_PAT está definida no terminal que abriu o claude (sem ela, o header Authorization vai vazio) e o PAT não expirou; (2) /mcp mostra o servidor github como connected; (3) o .mcp.json mantém o header X-MCP-Toolsets: context,repos,issues,pull_requests,actions, pois sem os toolsets as ferramentas de issues, PRs e Actions não são carregadas. Reinicie a sessão depois de alterar. Em erro, registre a mensagem exata (sem colar o token) e acione a TI; nunca desabilite a verificação de SSL.

Testes lentos ou com timeout na máquina

Nos relatórios, falhas de timeout (vitest worker, locator.fill) apareceram com a máquina lenta e foram classificadas como prováveis causas ambientais; reexecute com a máquina ociosa antes de investigar o código.

12.Limitações conhecidas

  • skills: só pré-carrega em subagentes; o TecLeader carrega as regras pela ferramenta Skill no início da sessão e após compact.
  • ${CLAUDE_PLUGIN_ROOT} é substituído pelo caminho do plugin ao carregar o corpo do agente e o da skill; em arquivos lidos com Read e no ambiente do Bash, não.
  • O caminho .mcp.json do Jira não foi validado com Zscaler ativo, e os nomes mcp__atlassian__* não foram verificados.
  • O carregamento das regras no TecLeader depende da instrução do agente (sem pré-carregamento na sessão principal); funcionou nos testes de validação.
  • Comandos de exemplo das references (lint, auditoria de dependências) não foram executados nos pilotos.
  • /compact não executa em modo -p.
  • Repositório: só o GitHub com GITHUB_PAT foi validado. OAuth do GitHub (sem header Authorization) não foi testado; Bitbucket, GitLab e Azure DevOps são experimentais e não foram validados. O deny de Bash é defesa em profundidade; a mitigação real é o token somente leitura.
